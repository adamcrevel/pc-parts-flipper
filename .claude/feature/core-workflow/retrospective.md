# Retrospective

## What happened
- **Cycle 0 (initial build, 14 builder tasks) needed a same-cycle retry round before it even reached UAT.** validate-lead's first review+test pass failed 6 of 14 builder tasks — T1 (root `build`/`dev`/`test` broke on a clean checkout because `packages/shared` wasn't built first, plus an ESLint `no-undef` false-positive on `.ts`/`.tsx`), T2 (a documented-but-untrue `createSale` contract, plus missing `UNIQUE` constraints on `sales(part_id)` and `teardown_results(purchase_id, expected_part_id)`), T3 (error-handler leaking raw DuckDB error text to the client), T7 (two parallel `accept` calls on the same Listing both succeeding and creating two Purchases — reproduced 4/4 real-concurrency runs — plus a stranded-pagination UI bug), T11 (Sale Listing `description` never pre-filled from the Part per Req 8), and T14 (a module-level singleton DuckDB connection racing under concurrency, reproduced 2/3 runs, plus a health-check timeout too short for this WSL environment's ~22-26s boot time). All six were fixed and re-verified in place without incrementing the cycle counter, per protocol — a 43% (6/14) first-pass rework rate on the initial build.
- **Cycle 1 exists because U0 (the Cycle 0 UAT run) failed on one concrete bug:** non-deterministic `LIMIT`/`OFFSET` pagination — every paginated `ORDER BY` in `listings.ts`, `purchases.ts`, `parts.ts`, `saleListings.ts`, `sales.ts`, and `profit.ts` lacked a secondary deterministic sort key, reproduced live on a 24-row Listings dataset where two consecutive pages lost 2 real rows and duplicated 2 others. Cycle 1 added T15 (the 6-file fix + a new `pagination.test.ts`) and T16 (an unrelated 1-warning lint fixup for an unused `JsonResponse` import), at 10 and 5 expected minutes respectively.
- **T15 itself needed an in-cycle retry because its own regression test was a false guard.** validate-lead's Cycle 1 validation passed the actual fix (RV15, TS15) but failed the cycle verdict: the committed `pagination.test.ts` used `SEED_COUNT = 24`, and reverting the real fix (the `, id ASC` tiebreaker) left that test green 6/6 runs — DuckDB returns a deterministic tie order at ~24 rows in this environment, below its parallel-scan threshold. The same revert against 500 tied rows reliably corrupted 44/500 IDs every time. Retry 1 raised `SEED_COUNT` to 500 for both the Listings and Purchases sub-tests; validate-lead's own independent break/restore against the production code (not the builder's say-so) confirmed the retried test now reliably fails when the fix is reverted (456/500 IDs corrupted, both for listings.ts:119 and purchases.ts:121) and passes 2/2 once restored.
- **Estimated token costs for reviewer and tester tasks were systematically far below their actual cost, almost every time a value was recorded.** Representative pairs (estimated → actual): T3 5,300 → 44,454 (8.4x); RV3 4,300 → 24,585 (5.7x); RV5 10,800 → 41,685 (3.9x); RV7 8,300 → 45,638 (5.5x); TS5 24,000 → 83,061 (3.5x); TS8 32,000 → 136,957 (4.3x); TS12 50,000 → 154,931 (3.1x); T16 2,100 → 24,980 (11.9x, despite running on `haiku`); T15's retry 15,000 → 69,200 (4.6x). Most reviewer/tester rows (RV1, RV2, RV4, RV6, RV8–RV14, TS1, TS2, TS4, TS6, TS7, TS9–TS11, TS13, TS14) have no `estimated_tokens` value recorded at all. The one clear outlier in the opposite direction is T11, estimated at 148,000 against an actual of 46,637 (3.2x over-estimate) — a single case, not a pattern.
- **One open assumption surfaced mid-fix, not corrected after the fact:** A11 (cycle 1, T15) records the pagination-tiebreaker design (fixed `id ASC` secondary sort, independent of each query's caller-selected primary direction) as a new decision made while fixing T15, not a reversal of an earlier wrong assumption — there was no prior pagination-ordering assumption on record to correct.
- No `context_split` or reactive model escalation pattern is visible in the task table: no task's real scope shows up split across more than one row (each MUST-FIX retry landed back on the same task id), and the only non-default `model` values (`haiku` on T16/RV16/TS16) were assigned up front for a 1-line lint fix, not escalated reactively.
- The worktree's commit history is a single squashed `Initial commit` with no per-task or per-cycle commits, so it adds no signal beyond what the task table and Cycle Log already show (no unusual fixup-commit clustering is visible because there is nothing to compare).

## Proposals
- Raise the default `SEED_COUNT`-style scale for any future regression test that exists to catch a race/ordering/tie-break bug in this DuckDB setup: 24 tied rows passed 6/6 even with the real bug present, while 500 reliably reproduced it every time. Add a one-line note to the builder/tester playbook for this repo: "tie-order and concurrency regression tests need ~500 contending rows/requests in this environment to be meaningful, not ~20-30."
- Stop recording `estimated_tokens` for reviewer (`RV*`) and tester (`TS*`) tasks as a single point estimate, or re-calibrate it upward by roughly 4-5x — as currently sized it undershot actual cost on nearly every row where both values exist, and is simply blank on most of the rest, so it isn't providing a usable planning signal for this task class.
- Given that 6 of 14 Cycle-0 builder tasks failed first review on genuinely different defect classes (build ordering, missing DB constraints, error-message leakage, a concurrency race, a Req-8 pre-fill gap, and an undersized health-check timeout), add a short pre-build checklist item to this project's builder brief covering the two defect types that recurred in spirit across tasks: "every endpoint that reads-then-writes under a uniqueness/one-time guarantee (accept/reject, sale creation, teardown) needs an atomic conditional update or a DB-level UNIQUE constraint, not just an application-level check" — T2 and T7 both independently hit this exact shape of bug in Cycle 0.
