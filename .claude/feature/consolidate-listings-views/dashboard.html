Goal

The "Listings" screen (/listings) and the "Listings Queue" screen (/listings-queue) are near-duplicates of the same underlying data (GET /api/listings) with different capability sets split across them for historical reasons. They are consolidated into one screen at /listings: the merged screen keeps everything "Listings" already has (an "Add Listing" button opening a top-of-page create form, and clicking a Listing's title opening/closing its inline edit form directly beneath its row) and gains everything "Listings Queue" already has (pagination, status/Source filters, a Source column, the eBay-scan/non-working badges, Accept/Reject actions, the Identify-Parts status column, bulk-select checkboxes with a sticky bottom action bar for triggering Identify Parts on many Listings at once, and auto-refresh while any visible row's identify-parts job is still running). The "Listings Queue" nav entry, route, and the components left with no remaining caller afterward are removed — not just unlinked, deleted. No server-side change is needed: every endpoint and field this merge uses (GET /api/listings with status/sourceId/limit/offset, GET /api/listings/ids, POST /api/listings/identify-parts/bulk, ListingSummary.identifyPartsStatus) already exists from the bulk-identify-parts feature. This is a client-side consolidation only.

Requirements

  • 1The "Listings Queue" nav entry and its /listings-queue route are removed entirely; /listings is the only screen for browsing, filtering, creating, editing, deciding (accept/reject), and bulk-triggering Identify Parts on Listings.
  • 2The Listings table is paginated (20 rows/page) and filterable by status and Source, replacing the screen's prior unpaginated, unfiltered fetch (limit: 1000).
  • 3Each row shows every column/badge either screen already had, none dropped: Title (with its existing photo indicator, eBay-scan badge, non-working badge), Source name, Status, Asking Price, Expected Resale, Difference, and an Identify-Parts status badge (no-job / in-progress / complete / failed, with a failed row's recorded error message visible on hover).
  • 4Each row has Accept/Reject actions, shown only while that row's status is 'open', disabled while that specific row's own accept/reject request is in flight.
  • 5Accepting a Listing creates its linked Purchase and shows a dismissable confirmation with a link to it; rejecting transitions its status; both refresh the table afterward.
  • 6If an accept/reject empties the current (non-first) page of the filtered result set, the view clamps back to the new last valid page instead of stranding the user on an empty one.
  • 7Each row has its own checkbox; a header checkbox is tri-state (unchecked / checked / indeterminate) and selects/deselects every Listing matching the currently-applied filters across every page, not only the current page's rows.
  • 8The selection — built by individual checkboxes or the header control — persists across page navigation and filter changes within the same visit to the screen.
  • 9A fixed bottom action bar appears once 1+ rows are selected, showing the exact count and an "Identify Parts" button; clicking it sends one request enqueuing identify-parts for every selected Listing and reports how many were newly queued, already active, or not found.
  • 10While any row visible on the current page has a non-terminal identify-parts status, the table refreshes automatically every 2 seconds; it stops once nothing visible is still non-terminal.
  • 11Clicking a Listing's title still opens/closes its inline edit form directly beneath its row, completely unaffected by Requirements 2-10 — the same ListingForm already used for both create and edit, including its own Identify Parts button, Expected Parts editor, and photo upload, keeps working exactly as it does today.
  • 12An "Add Listing" button still opens the existing top-of-page create form; successfully creating a Listing refreshes the table so the new row appears.
  • 13No dead code remains afterward: the old Listings Queue page component, its dedicated table component, and any filter/action-bar files left with no remaining caller once the merge is done are deleted, not merely disconnected from the router.
