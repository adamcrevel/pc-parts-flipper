Goal

The full-screen photo viewer a Listing's photo thumbnails open (apps/web/src/features/listings/photo-lightbox.tsx) only closes via its own X button today — clicking the empty space around the photo does nothing, even though the component's own doc comment says it is "built on the shared Dialog primitive (Radix), which already owns ... click- outside-to-close." Root cause, confirmed by reading the component: DialogContent's own className sets h-screen w-screen with flex items-center justify-center, so its DOM bounding box covers the entire viewport — there is no pixel on screen actually "outside" DialogContent for Radix's own outside-click detection to ever fire against. The empty-looking space around the centered photo is visually background, but structurally still inside DialogContent. This fixes that: clicking anywhere in that empty space (not the photo, not the Close/Previous/Next buttons) closes the lightbox, the way a user expects a click on an image lightbox's backdrop to behave.

Requirements

  • 1Clicking anywhere in the lightbox's visible area that is not the photo itself and not one of its three buttons (Close, Previous, Next) closes the lightbox.
  • 2Clicking the photo itself does not close the lightbox — this is the one thing a user is actually looking at; an accidental click on it should not dismiss the view, matching the conventional lightbox pattern (click the image to inspect it, click away from it to leave).
  • 3Clicking Close continues to close the lightbox exactly as it does today (and does not fire the close logic twice).
  • 4Clicking Previous or Next continues to navigate to the adjacent photo exactly as today, and does not also close the lightbox — a navigation click must never be mistaken for a backdrop click.
  • 5Everything else about the lightbox is unchanged: Escape still closes it (unaffected, since this is Radix's own keyboard handling, untouched by this fix), Left/Right arrow-key navigation and wraparound are unchanged, the photo counter badge's own appearance/position is unchanged.

T1 was reopened in place with a MUST_FIX appended to its own description (stabilize with the codebase's existing waitFor(predicate, timeoutMs) polling helper, per bulk-identify-parts-ui.test.tsx/listings-page.test.tsx), and T1/R1/TE1 reset to not_started, still inside cycle 0.
  • Cycle 0 → Cycle 1 transition: R1's second pass (after the flakiness fix) verified the fix itself was correct and stable (44/44 clean reruns), but surfaced a second, independent gap: Requirement 3's "Close does not fire the close logic twice" guard had zero test coverage, because PhotoUpload's onClose={() => setLightboxIndex(null)} is idempotent — a single call and a double call produce an identical DOM outcome, so no existing test (including the pre-existing Close-button test) could distinguish them. Because T1 had already consumed its one free in-place retry this cycle (for the flakiness fix), this second finding could not be folded into a third in-place attempt and instead opened Cycle 1. Cost of Cycle 1: two new tasks, T2 (builder, expected_minutes 10, actual_tokens 39,843) and its paired R2/TE2 reviews (expected_minutes 10 each, actual_tokens 51,094 and 38,576) — all three completed in a single 4-minute window (22:26–22:48), i.e. the fix itself was trivial (a test-only addition, zero photo-lightbox.tsx change per T2's own description) but still required a full builder→reviewer→tester lap plus a fresh UAT pass (U0, actual_tokens 91,931) because UAT had not yet run against the feature.

Proposals

  • Have T1's own task description require a Requirement-3 double-fire test up front, not just the stopPropagation() code change.The gap R1 found in cycle 1 — that PhotoUpload's idempotent onClose makes a single vs. double call indistinguishable through any PhotoUpload-mounted test — was knowable from the Requirements alone (R3 explicitly says "does not fire the close logic twice") without touching the implementation first. Future plans for components with an idempotent callback prop should add a line to the builder task like: "if the callback bound to the no-double-fire guard is itself idempotent, write the regression test by mounting the component directly with a spy, not through its idempotent caller" — this would have produced T2's test as part of T1 and skipped Cycle 1 entirely (saving roughly the T2+R2+TE2+U0 token cost, ~221,000 tokens, and the 4-minute build-review-test lap plus a second UAT pass).
  • Size R1-equivalent review tasks that re-verify all N requirements after an in-place retry at a slightly higher expected_minutes/token budget than a first-pass review, since this plan's data point (15 expected minutes, 202,340 actual tokens — by far the feature's largest single cost) shows full-requirement re-verification after a retry costs materially more than a first pass over fresh code; the estimate didn't anticipate that a retry review re-walks every requirement, not just the one that changed.
