Goal

This feature adds three related capabilities to the Listings page and its AI identification pipeline, confirmed with the user across four clarifying questions before any plan was drafted. 1. Per-part notes. Each Expected Part gains a freeform notes field, editable in the Expected Parts editor the same way brand/partNumber/description already are. When identify-parts re-runs for a listing, the AI model is handed that listing's *current, live* Expected Parts (including any notes on them, and any manual edits made since the last run) as prompt context — not the raw stored result of whichever job ran previously. The model is instructed to take those notes into account as corrections or clarifications while forming its new identification, and to carry each one forward onto whichever of its own newly-identified parts it judges corresponds to the original. Confirmed explicitly with the user: this matching is the model's own judgment call, never a deterministic field-based rule — notes frequently exist *because* a brand or part number was wrong, so the very field a mechanical match would key on is exactly what the note is correcting. Because identify-parts is a full-replace operation (every existing Expected Part is deleted and the model's new output is inserted in its place — identifyPartsWorkerPool.ts's persistIdentifiedParts), a note only survives a re-run if the model reproduces it on its new output; nothing else carries it forward. 2. Unpriced-parts indicator. A new "Unpriced" column on the Listings table shows whether a listing has at least one Expected Part with no estimated resale value, reusing the sortable-column infrastructure the listings-sortable-columns feature already built (ListingSortField, SORT_KEYS, SortableHeader). Confirmed with the user: ascending sort on this column should show unpriced listings first (finding work still needing pricing is the point of the column), the deliberate inverse of every existing column's plain-ascending order. 3. Unpriced-row highlight. The Expected Parts editor visually flags any row with no estimated resale value, using the same error-style visual language the editor already uses for a real validation failure (the AlertCircle indicator next to a row with a bad category/description/ price). Confirmed with the user: this highlight appears only while editing an already-saved (existing) listing — never while creating a new one, where an unpriced row is simply the normal, expected state of every field not yet filled in.

Requirements

  • 1ExpectedPart and ExpectedPartInput (packages/shared/src/listings.ts) gain a notes field: freeform text, editable in the Expected Parts editor the same way brand/partNumber/description are, round-tripping through both create and the full-replace update/save path.
  • 2When POST /api/listings/:id/identify-parts re-runs for a listing that already has Expected Parts, the AI prompt (buildIdentificationPrompt) includes that listing's *current, live* Expected Parts — fetched via listExpectedPartsByListing immediately before the prompt is built, not the stored result of any previous identify-parts job — including each part's own notes, as explicit context.
  • 3The prompt instructs the model to take each note into account as a correction or clarification when forming its new identification (not merely echo it back unread).
  • 4The prompt instructs the model to carry each note forward onto whichever of its own newly-identified parts it judges corresponds to the original part the note was on, writing it into that part's own notes output field. Matching which new part a note belongs to is the model's own judgment call; no deterministic field-matching logic (by category, brand, part number, or array position) is written in code anywhere in this change.
  • 5A newly-identified part the model judges has no corresponding previous note — including every part of a first-ever identification, where the listing had no previous Expected Parts at all — gets an empty notes value (""), never null and never a placeholder string.
  • 6The per-part notes the model returns is persisted to the database for every Expected Part the full-replace identifyPartsWorkerPool.ts's persistIdentifiedParts creates, the same write path already used for the model's other per-part fields (brand, partNumber, confidence, source).
  • 7The second AI pass (visual comparison, visualComparisonPrompt.ts/visualComparisonParser.ts) never modifies a part's notes value — it updates only brand/partNumber/identityCandidates (confirmed: VisualComparisonUpdate carries no notes field today, and this change must not add one).
  • 8The Listings table (listing-list.tsx) gains a new sortable "Unpriced" column indicating whether a listing has at least one Expected Part with no estimated resale value (estimatedResaleValue === null).
  • 9The Unpriced column follows the exact click-to-sort mechanics listings-sortable-columns already built: clicking it while inactive makes it the active sort field, ascending; clicking it again while active reverses direction; clicking a different header replaces it outright.
  • 10Ascending sort on the Unpriced column lists every listing with at least one unpriced Expected Part before every listing with none — the deliberate inverse of every other sortable column's plain-value ascending order, confirmed with the user as the direction they actually want.
  • 11A listing with zero Expected Parts at all is treated as *not* having an unpriced part (see Assumption A5) — stated here explicitly rather than left to whatever an implementation happens to default to.
  • 12In the Expected Parts editor, a row whose estimated resale value is empty is visually flagged with an error-style highlight (the same AlertCircle treatment already used for a genuine validation failure on that row).
  • 13The Requirement 12 highlight is shown only while editing an already-saved (existing) listing — it never appears while creating a new listing, where every row legitimately starts unpriced.
