Goal

The Listings table's "Pricing Status" column currently shows only two values, computed from a boolean hasUnpricedParts (true if at least one fetched Expected Part has a null estimatedResaleValue, false otherwise — including, by .some's own semantics on an empty array, a listing with zero Expected Parts at all). User-reported bug: a listing that has not yet had its parts identified (zero Expected Parts) — or one whose parts exist but are *all* unpriced — is shown as "Fully Priced", which is wrong: neither listing has actually had any pricing work done on it at all. This feature replaces the two-value model with three, computed from the same Expected Parts data already fetched, no new stored column: - "Not Priced" — zero Expected Parts (not yet identified), or at least one Expected Part exists but every one of them is unpriced (zero priced out of however many exist). - "Partially Priced" — at least one Expected Part is priced AND at least one is unpriced (a genuine mix). - "Fully Priced" — at least one Expected Part exists and every one of them is priced. Ascending sort keeps the existing "most work still needed sorts first" direction, extended to the third state: Not Priced, then Partially Priced, then Fully Priced.

Requirements

  • 1A Listing's Pricing Status is computed as exactly one of three values — not_priced, partially_priced, fully_priced — replacing the current two-value hasUnpricedParts boolean entirely (not added alongside it).
  • 2"Not Priced" is the result when the Listing has zero Expected Parts.
  • 3"Not Priced" is also the result when the Listing has one or more Expected Parts but every one of them has a null estimatedResaleValue (none priced at all) — the specific gap the user reported.
  • 4"Partially Priced" is the result only when the Listing has at least one priced Expected Part and at least one unpriced Expected Part, both true at once.
  • 5"Fully Priced" is the result when the Listing has at least one Expected Part and every one of them has a non-null estimatedResaleValue.
  • 6The Listings table's Pricing Status column renders the correct one of three distinct labels — "Not Priced", "Partially Priced", "Fully Priced" — for every row, never blank and never a two-value result.
  • 7Ascending sort on the Pricing Status column lists every "Not Priced" listing first, then every "Partially Priced" listing, then every "Fully Priced" listing — extending the existing unpriced-first convention to the new third bucket, not just preserving it for the old two.
  • 8Descending sort on the Pricing Status column is the exact reverse of Requirement 7's order.
  • 9Sorting by Pricing Status still composes correctly with pagination across the whole filtered dataset (a bucket boundary that falls mid-page is not re-sorted independently per page), matching the existing proof already established for every other sortable column.
