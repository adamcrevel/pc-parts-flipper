Feature

Status done · cycle 1 of 3 · refreshes in 5m 0s

Goal

Whenever an Expected Part becomes fully identified (it has both a brand and a part number), the system automatically looks up and attaches an estimated resale value for it in the background — no user action needed. This happens right after an identify-parts job finishes, and again whenever a Listing is saved with a part that just became fully identified (for example, the user typed in a part number by hand). Prices are cached by (category, brand, part number) and reused across all Listings, refreshed once a day, and never overwritten once a user has set or edited that part's price themselves.

Requirements

  • 1As soon as an identify-parts job finishes saving its identified parts, any resulting Expected Part that has both brand and part number automatically gets its estimated resale value researched — no further action needed.
  • 2The researched value is a used, working/good-condition price for that specific category, brand, and part number.
  • 3An Expected Part missing a brand or part number is never auto-researched.
  • 4Saving a Listing's Expected Parts in the UI (creating or editing) triggers the same automatic research for any part that becomes fully identified and doesn't already have an estimated resale value.
  • 5Price research always runs as a background queued job, never synchronously within the request that triggered it — true for both the identify-parts trigger and the manual-save trigger.
  • 6Prices are cached by the combination of category, brand, and part number, and shared across all Listings rather than researched separately for each Listing.
  • 7If a (category, brand, part number) combination already has a cached, non-null price, an Expected Part gets that price right away, with no new research call.
  • 8A once-daily scheduled job re-researches every (category, brand, part number) combination in the cache — whether or not it currently has a price — and updates the cache.
  • 9The first time a (category, brand, part number) combination appears with no cached price, a cache row is inserted immediately with no price, so the daily refresh job will find and retry it even if the first research attempt fails or is still running.
  • 10A failed or inconclusive research attempt never deletes or blocks that combination's cache row — it stays in place with a null value, ready for the next daily refresh.
  • 11If a research attempt succeeds but finds no confident price, the cached value stays null — never a guessed or zero value.
  • 12A later refresh that fails to find a value never overwrites an already-cached price with null — only a new successful result replaces the cached value.
  • 13If two writers hit the same (category, brand, part number) for the first time at nearly the same moment (two different Listing saves, or a save racing the daily refresh), this never produces two diverging cache rows or two duplicate background jobs for that combination.
  • 14If a user manually enters or edits an Expected Part's estimated resale value, that row is never later overwritten by automatic price research or the daily refresh.
  • 15Editing any field of an Expected Part row stops that row from being auto-managed by price research going forward — the same rule that already governs the "AI suggested" flag: touching a row means the user now owns it. One consistent rule, not two.
  • 16After a user clicks "Identify Parts," the status text already shown for that job keeps reflecting progress until every price research triggered by that job's completion has also finished (found a price, or exhausted its attempt) — not just until the identify-parts job itself completes.
  • 17Price research triggered only by a manual Listing save (not by clicking "Identify Parts") has no dedicated status shown in the UI — the price just appears once it's ready, like any other field that gets filled in the background.

## Proposals

- For schema-adding tasks (this feature's T1): add "update db.test.ts's EXPECTED_COLUMNS
  fixture and migrate.ts's rebuild lists for every new table/column" as an explicit sub-item of
  the schema task itself, not something left for a reviewer/tester to discover after the fact —
  this is now the second feature in this codebase (after ai_confidence/ai_source, per A12) to
  hit exactly this gap.
- When a task's description cites a specific measured number in a doc comment (a cyclomatic
  complexity figure, a test count, a column count), add a review-checklist line requiring the
  reviewer to re-run the measurement live rather than trust the stated number — this caught T9's
  stale "10" and should be made a standing step rather than something each reviewer has to
  reinvent per task.
- When a task (like T4 here) is large enough to need the two-way null/undecided-vs-claimed
  semantics distinction A21 ended up specifying, write that three-state model into the task's own
  description up front rather than let it surface as a must_fix after the fact — concretely, any
  future task introducing a nullable "ownership" or "source" flag on a per-row field should be
  checked at spec time for exactly this conflation ("does null mean one thing or two?"), since this
  feature hit the same bug shape twice (T4's original finding, then T13's MF1) before it was fully
  closed.
- Do not dispatch a task's reviewer and its tester in parallel when the tester is expected to
  author or mutate the same file the reviewer reads live (true for both A19's Cycle-0 collisions
  and R13/TE13's Cycle-1 collision on expected-parts-editor.tsx) — serialize review-then-test (or
  test-then-review) for any task where the reviewer's own verification method is live mutation
  against a file the tester is also actively writing.
- Fix the child-cost --tag measurement gap (A18): every task in this plan shows
  actual_tokens: null, so this retrospective — and any future one for this worktree — cannot
  measure real token cost per task or per cycle, only estimated_tokens. Without a working
  measurement path, cycle-cost analysis in this process is permanently blind to its most basic
  question: how many tokens did a cycle actually cost versus Cycle 0.
