Goal

The Listings Queue screen (apps/web/src/routes/listings-queue-page.tsx + listings-queue-table.tsx) gains bulk identify-parts triggering. Each row gets its own checkbox; a header control selects or deselects every Listing matching the currently-applied filters across every page of results, not just the current page, and is tri-state (unchecked / checked / indeterminate) to reflect partial selection. The selection persists across page navigation and filter changes within the same visit — paging through results or changing the status/Source filter never silently drops what was already selected. Whenever one or more Listings are selected, a fixed action bar appears (bottom of the viewport) showing the selected count and an "Identify Parts" button. Clicking it sends one request that enqueues an identify-parts job for every selected Listing, reusing the exact same per-listing concurrency rule the existing single-listing Identify Parts button already relies on (a Listing with a job already in flight is skipped, never given a second one) and reports back a summary — how many were newly queued, how many were already in progress, how many ids no longer existed. Separately, every row in the queue table shows its own identify-parts job status at a glance — no job yet, waiting/in progress, complete, or failed, with the failure reason visible on hover for a failed row — without the user opening that Listing's detail view. While any row visible on the current page is in a non-terminal state, the table refreshes automatically so progress is visible without a manual reload, stopping once nothing visible is still in flight.

Requirements

  • 1Each row in the Listings Queue table (listings-queue-table.tsx) has its own checkbox; checking it adds that Listing to the current selection, unchecking it removes that Listing from the selection.
  • 2A header checkbox control reflects and toggles selection of every Listing matching the currently-applied status/Source filters, across every page of results — not only the rows on the current page.
  • 3The header control is tri-state: unchecked when none of the filtered Listings are selected, checked when all of them are, indeterminate when some but not all are selected.
  • 4The selection set — however it was built, by individual checkboxes or by the header control — persists across page navigation and filter changes within the same visit to the screen; it is never silently cleared by paging or changing filters.
  • 5Whenever the selection is non-empty, a fixed action bar is shown (bottom of the viewport) displaying the exact count of currently selected Listings and an "Identify Parts" button.
  • 6Clicking the bulk "Identify Parts" button sends one request that enqueues an identify-parts job for every currently selected Listing.
  • 7The bulk request reuses the exact same per-listing concurrency rule the existing single-listing Identify Parts button (identify-parts-button.tsx) already relies on: a Listing that already has a non-terminal identify-parts job is left alone, never given a second, duplicate job.
  • 8After a bulk request completes, the user is shown a summary of its outcome: how many Listings were newly queued, and how many were skipped because a job was already active for them.
  • 9A selected id that no longer corresponds to any Listing (e.g. since deleted) is reported distinctly in the summary rather than silently dropped or causing the whole request to fail.
  • 10Each row in the Listings Queue table shows its own identify-parts job status without the user opening that Listing's detail view: visually distinguishable states for "no job yet", "waiting/in progress" (any non-terminal stage), "complete", and "failed".
  • 11A row whose latest identify-parts job failed lets the user see the recorded failure reason (e.g. on hover) directly from the queue table, without opening the Listing.
  • 12While any row visible on the current page has a non-terminal identify-parts job, the table's statuses refresh automatically on an interval, so progress (waiting -> in progress -> complete/failed) is visible without a manual page reload; refreshing stops once nothing visible on the current page is still non-terminal.
  • 13Triggering identify-parts in bulk never bypasses or weakens the existing single-listing trigger's own behavior — the Identify Parts button on a Listing's own detail view, and its polling/result-handling (identify-parts-button.tsx), are unchanged.
