Goal

Both AI parsing stages of the identify-parts pipeline — first-pass identification (parseIdentificationResponse) and the second-pass visual comparison (parseVisualComparisonResponse) — share one fragile helper, stripCodeFence() (apps/server/src/ai/identificationParser.ts). It only strips a markdown code fence when the model's *entire* trimmed response starts with and ends with a bare ` fence, with nothing else. If the model adds even one sentence of commentary before or after the JSON (e.g. "I can't fully confirm this, but here's my comparison:\n``json\n[...]\n`"), despite the prompt's explicit "no commentary before or after" instruction, stripCodeFence returns the text unchanged, JSON.parse fails on the mixed prose+JSON, and the whole job fails — surfacing as AppError(502, 'The AI model did not return a JSON array for visual comparison') or the equivalent identification-stage message — **even when the model produced a genuinely valid JSON payload**, just not perfectly isolated at the exact string boundaries. This has been observed as a real, repeated failure during live identify-parts runs. Confirmed via source read (the anchoring regexes require an exact whole-string match) and via the test suite (neither parser's tests exercise a fenced response, or any leading/trailing-prose case, at all). The fix adds a tolerant fallback: when a direct parse (after the existing fence-strip, which stays as the cheap first attempt) still fails, extract the outermost bracketed JSON payload — the substring from the first {/[ to the last matching }/] in the raw text — and retry parsing that substring before giving up. This recovers the common "valid JSON surrounded by incidental prose" case without weakening the existing contract that genuinely malformed output (no JSON present at all) still fails loudly with the same AppError(502)`.

Requirements

  • 1A model response that is a bare, well-formed JSON payload (today's only fully-working case) continues to parse exactly as it does today — this fix changes nothing about the already-succeeding path, confirmed by the existing test suite passing unchanged.
  • 2A model response that is a pure code-fence-wrapped JSON payload with nothing else ( `json\n[...]\n` ) continues to parse correctly via the existing stripCodeFence direct-parse path, unaffected by this fix — confirmed already covered by one pre-existing test per parser (found during implementation; the plan's original premise that this case had zero coverage was wrong, corrected in Assumption A6 rather than left standing).
  • 3A model response that includes incidental prose *before* a code-fenced or bare JSON payload (e.g. a caveat sentence) is successfully parsed by extracting the JSON payload rather than failing outright, in both the identification and visual-comparison parsers.
  • 4A model response that includes incidental prose *after* a code-fenced or bare JSON payload is successfully parsed the same way, in both parsers.
  • 5A model response containing no JSON payload at all (e.g. a plain-language refusal) still fails with the same AppError(502) it does today, with the same log line at Error level — this fix narrows false failures, it does not loosen the "structural failure is fatal" contract for genuinely unparseable output.
  • 6The new fallback extraction is only ever attempted after a direct parse has already failed — a response that already parses cleanly never pays its cost, and its own behavior is covered by a dedicated unit test independent of either parser (so a future change to one parser's call site can't silently stop exercising it).
