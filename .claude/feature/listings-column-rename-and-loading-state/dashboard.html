Goal

Three small, user-requested tweaks to the Listings table (listing-list.tsx/listings-page.tsx): 1. Rename three column headers: "Difference" -> "Expected Profit", "Identify Parts" -> "Sourcing Status", "Unpriced" -> "Pricing Status". Every rename is a display-label change only — the underlying ListingSortField identifiers (difference, identifyParts, unpriced) sent to the server and the values each column actually shows are unchanged. 2. The renamed "Pricing Status" column's cell, previously a binary "Unpriced" pill-or-nothing, now always carries one of two named values: "Fully Priced" (no unpriced Expected Part) or "Partially Priced" (at least one unpriced Expected Part) — the same underlying hasUnpricedParts boolean, given both of its states an explicit label instead of only the true case. 3. Clicking a sortable column header to change sort order currently leaves the table showing the previous (stale) data, unchanged, until the new page arrives — confirmed by the user: this has led to an accidental second click while the first request is still in flight. The table now enters a visible loading state for the duration of any user-triggered refetch (sort change, filter change, page change), and every sortable header is disabled for that same duration, so a second click cannot queue a redundant request.

Requirements

  • 1The "Difference" column header is renamed to "Expected Profit". Its sort field identifier (difference), its computed value (comparison.difference), and its $ formatting/color coding are all unchanged.
  • 2The "Identify Parts" column header is renamed to "Sourcing Status". Its sort field identifier (identifyParts) and its per-stage badge values are unchanged. This rename is scoped to the Listings table's column header only — the separate "Identify Parts" action buttons elsewhere on the page (the per-row IdentifyPartsButton, the bulk-action bar's button) keep their existing wording; they are a different control for a different purpose that happens to share the same words today.
  • 3The "Unpriced" column header is renamed to "Pricing Status". Its sort field identifier (unpriced) and its underlying hasUnpricedParts boolean are unchanged.
  • 4The Pricing Status column's cell always renders one of two values, replacing the previous badge-or-nothing rendering: "Partially Priced" when hasUnpricedParts is true, "Fully Priced" when it is false.
  • 5Ascending sort on the Pricing Status column still lists every "Partially Priced" listing before every "Fully Priced" one (the existing, deliberately-inverted sort direction is unchanged by this relabeling).
  • 6While a GET /api/listings request triggered by a sort-header click, a filter change, or a page change is in flight, the Listings table visibly enters a loading state: its existing rows stay on screen (never replaced by a blank/spinner-only view) but are visually marked as stale until the new result lands.
  • 7While that loading state is active, every sortable column header is disabled (not clickable) — a click during this window has no effect, which is what stops the double-request the user described.
  • 8The background 2-second polling reload (while a visible row's identify-parts job is still non-terminal) does not trigger the Requirement 6/7 loading state — that reload is intentionally silent today, and nothing about this feature changes it, so the table does not flicker every 2 seconds while a job is running.
