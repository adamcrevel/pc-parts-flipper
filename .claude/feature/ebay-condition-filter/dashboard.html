Goal

eBay scans search only used-condition items (conditionIds 3000, 4000, 5000, 6000, 7000: Used, Very Good, Good, Acceptable, For Parts or Not Working), since new and refurbished listings rarely sell below market rate and so rarely offer a profitable flip. A Listing imported from a "For Parts or Not Working" item is flagged non-working in the UI. When Identify Parts runs on such a Listing, the AI identification pass also reads the listing's own description to tell, per part, whether it's specifically called out as broken. If one or more parts are named, only those are marked non-working and every other part on the Listing is marked working. If the description gives no determinable breakdown, every part on the Listing is marked non-working instead (safer than guessing). The user can always set or change any part's working status by hand in the UI, overriding the AI's read or correcting a manually-entered part (e.g., a case is rarely the broken component, even on an otherwise non-working build). A part marked non-working gets a flat $1 estimated resale value automatically as soon as it's fully identified, instead of running real AI price research, and that $1 never enters the shared price cache used by other Listings. A part marked working is priced exactly as it already is today — real cached or AI-researched value — regardless of whether its own Listing is flagged non-working. Changing a part's working status by hand resets its price to undecided (unless the user already set the price themselves), so the next save re-prices it correctly under its new status instead of keeping a stale value from the old one.

Requirements

  • 1Every eBay Browse API search call made by the automated scan restricts results to conditionIds 3000, 4000, 5000, 6000, and 7000 (Used, Very Good, Good, Acceptable, For Parts or Not Working).
  • 2The condition filter excludes conditionIds 1000, 1500, 1750 (New, New Other, New with Defects) and 2000, 2010, 2020, 2030, 2500, 2750 (every Certified/Excellent/Very Good/Good/Seller Refurbished tier and Like New).
  • 3The condition filter is always applied to every query, combined with the existing optional per-Source max-price filter when one is configured — never a separate opt-in.
  • 4A Listing imported by an eBay scan whose source item's conditionId is 7000 (For Parts or Not Working) is flagged as non-working, stored on the Listing itself, and shown clearly in both the Listings queue table and the Listing detail/edit view.
  • 5A manually-entered Listing is never flagged non-working.
  • 6Every Expected Part on a Listing NOT flagged non-working has its working status set to exactly 'working' — never left undetermined — whether it was identified by Identify Parts or entered manually.
  • 7When Identify Parts runs on a non-working Listing, the AI identification pass determines, for each identified part, whether the listing's own description specifically indicates that part is broken/non-functional, separately from the part's own brand/category/condition fields.
  • 8If the description specifically names one or more parts as broken, only those named parts are given working status 'non_working'; every other identified part on that same Listing is given 'working'.
  • 9If the description gives no specific, determinable breakdown at all (for example, only a generic "sold as-is, untested" statement with no part singled out), every identified part on that Listing is given working status 'non_working' instead of guessing which one is actually broken.
  • 10A manually-entered Expected Part on a non-working Listing defaults to working status 'working' unless the user sets it otherwise (Requirement 11) — Identify Parts' description analysis never runs for a manually-entered part.
  • 11The user can set or change any Expected Part's working status (working / non-working) directly in the UI, overriding whatever Identify Parts determined or whatever the default was.
  • 12The background price-estimation trigger's own eligibility check requires an Expected Part's working status to be exactly 'working', in addition to its existing requirements (brand and part number both known, no estimated resale value of its own yet) — a part whose working status is 'non_working' is never passed into the cache/research pipeline at all, regardless of whether it happens to already carry a value.
  • 13An Expected Part with working status 'non_working', the moment it becomes fully identified (brand and part number both known) with no estimated resale value of its own yet and no price already owned by the user, is automatically assigned an estimated resale value of exactly $1 instead of running real AI price research.
  • 14The $1 assignment under Requirement 13 never enters the shared part_price_cache — it is specific to that one Listing's actual item, not a market-price fact to share with other Listings of the same category/brand/part-number.
  • 15A $1 value assigned under Requirement 13 follows the same ownership rule as any other auto-assigned price (price_source's existing three-state rule): a user who edits or clears it takes manual ownership of that row, and it is never auto-reclaimed or overwritten afterward.
  • 16A part the user has already priced themselves (price_source already 'manual') is never overwritten by the $1 assignment, regardless of its working status.
  • 17Changing a part's working status in the UI (Requirement 11), when that part's price is not already user-owned, clears its estimated resale value and returns its price ownership to undecided — so the next save re-evaluates its price correctly under the new status via Requirement 12's gate (a part moved to 'working' becomes eligible for real research; a part moved to 'non_working' becomes eligible for the $1 assignment via Requirement 13) instead of leaving a stale price from its old status in place.

Proposals

  • Add an export/import-removal check to the builder's own self-review step for any task that edits a file already imported elsewhere, since MF-4 was the most expensive single finding this feature produced (56 test failures, a critical-severity crash on every mount) and was entirely mechanical: grep every file the task's diff touches for export function <name> deletions and import line replacements before handing off, rather than relying on the next reviewer to catch it live. This would have caught both the deleted initialExpectedPartRows export and the clobbered ExpectedPartsEditor import in T6 itself, instead of needing a whole extra cycle (T9 + R9 + TE9) to fix.
  • Add a "same-value no-op" check to feature-brief/task specs for any new UI toggle/setter that can reset a derived field (like a price) as a side effect, given MF-5's class of bug (re-click the active state, lose real data) is a recognizable pattern whenever a handler's reset logic isn't gated on an actual value change. Naming this explicitly in T6's own task spec next time would avoid relying on TE6 to find it by construction.
  • When a task touches a shared-cache propagation path (like propagateCachedPriceToExpectedParts) in the same diff as a new per-row exclusion field (like working_status), require the reviewer to explicitly trace every *other* write path into that same table, not just the task's own new code— MF-2 was invisible from T5's own diff because the WHERE clause that needed the new column was in a function T5 didn't modify at all (it only added the column and the one trigger check). This is the one finding here that a single task's own review structurally cannot catch; R5 did catch it by being told to construct a specific counter-example, which is the right technique — formalize "trace every write-path into the touched table, not just the touched function" as a step for cross-cutting tasks like T5.
  • Fix the token-measurement tagging gap rather than keep reporting null.Two separate cycles (A10, A16) hit the same root cause: whatever dispatch mechanism measure-child-cost.py expects (an AGENT_TAG: <tag> line inside the child's own transcript) isn't reachable through the _task tool this orchestrator used, which has no description/tagging parameter to embed that marker. 26 of 27 task rows in this feature's own table carry null for actual_tokens as a result — essentially the entire cost-accounting column is unusable. This is worth fixing once, upstream (either give _task a tagging parameter or point the measurement script at whatever identifier _task does expose), rather than re-discovering and re-documenting the same gap on every future feature's plan.md.
