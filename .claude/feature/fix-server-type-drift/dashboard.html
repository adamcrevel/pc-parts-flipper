Goal

npm run build -w apps/server (and the root npm run build) currently fail with ~40 tsc errors. Root cause, confirmed by reading every affected file: apps/server/src/db/types.ts hand-maintains a local mirror of 8 DuckDB row shapes that already exist, field-for-field identical once corrected, in packages/shared — a second copy that several past features updated on one side (almost always packages/shared, since that is what routes/the web UI needed) without updating the other. In every one of the 9 currently-drifted entities, the real DB query function (apps/server/src/db/queries/*.ts) already builds the complete, correctly-named object matching the real schema and packages/shared — only the stale local interface declaration blocks tsc. One entity (PricePartsJob) also has a genuine one-line code gap: its query's mapRow never reads the updated_at column into the returned object, even though the column exists and is written on every update. A sibling connector-staging type (apps/server/src/connectors/types.ts's CandidateListing) is missing one field the same way. Rather than re-fix this second copy in place (which only repeats the bug's precondition — two declarations of the same shape, free to drift again next feature), this plan eliminates the duplication for every entity where it is pure staleness with nothing deliberately different left: of db/types.ts's 12 exported entity types, 8 (Source, Listing, Purchase, TeardownResult, Part, SaleListing, Sale, plus their 6 backing enums) are exact duplicates of packages/shared's own types once corrected, with no remaining reason to keep two copies. One more, ExpectedPart, has a single deliberate, documented difference (packages/shared's version makes aiConfidence/aiSource/priceSource optional for backward compatibility with callers built before a past feature; the DB-row version keeps them required since every migrated row already has them) — still safely collapsible, since optional is a strict superset of required, but called out rather than silently flattened. The remaining 4 (SourcingAttempt, ReferencePhoto, PartPriceCacheEntry, PricePartsJob) correctly have no packages/shared counterpart at all — they never cross the HTTP boundary (internal job-queue/cache/training-data concerns) — and stay exactly where they are. This has no runtime or test impact today — the live dev service runs via tsx watch (no compile step) and the test suite runs via vitest's esbuild transform (no type-check) — which is why the drift went unnoticed across multiple features. Fixing it is still worth doing: a broken build blocks any future CI/tooling that type-checks, and collapsing the duplication (rather than only re-syncing it) removes the precondition for this exact bug recurring.
