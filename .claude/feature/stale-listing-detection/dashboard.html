Feature

Status building · cycle 3 of 3

· 5m 0sAuto-refresh is off.

Goal

Stop the Listings queue from silently accumulating dead listings, and stop them from cluttering the actionable queue once found. Today a scan only ever imports new candidates — nothing ever notices when a previously-imported, still-open Listing has sold or been delisted on the marketplace it came from, so it sits forever requiring the same Accept/Reject decision as a listing that's still live. This feature adds a direct per-item recheck to the scan pipeline that, once it confirms a Listing is genuinely gone, automatically moves it to a new terminal removed status — out of the actionable Accept/Reject flow entirely, filterable separately, same as accepted/rejected already are — while still showing why (sold vs. simply no longer listed) via a visible badge.

Requirements

  • 1ListingStatus gains a new terminal value, 'removed' — a Listing whose own marketplace page confirms it's gone, auto-transitioned there by the scan pipeline (Requirement 3), never by a user action. Listing separately gains marketplaceStatus ('sold' | 'removed' | null) and marketplaceStatusDetectedAt (ISO timestamp, or null) — nullable, defaulting to null for every existing and newly-created Listing, carrying *why* a removed-status Listing is gone (the status field alone can't distinguish sold from simply delisted). Neither marketplaceStatus/ marketplaceStatusDetectedAt, nor the 'removed' status value, is ever settable through the public POST /api/listings / PUT /api/listings/:id request body — only the scan pipeline (Requirement 3) ever writes them.
  • 2Accept/Reject stops being offered for a removed-status Listing — this already falls out of the existing listing.status === 'open' guard the Accept/Reject buttons are already conditioned on (apps/web/src/features/listings/listing-list.tsx); no new conditional logic duplicates it.
  • 3Each scan pass, for the Source being scanned, considers every one of its already-imported Listings still in open status whose externalItemId did not appear among this pass's connector results. For each one, before marking anything, run a **direct per-item recheck against that specific listing's own marketplace page** — never inferred purely from its absence in one page of search results, since a scan can legitimately return fewer/different results for reasons unrelated to the item being gone (a maxPrice edited, a query term changed, a connector's own page-size limit). Only when that direct recheck itself confirms the item is gone does the Listing atomically transition open → removed (guarded the same way transitionOpenListing already atomically guards every other status transition, so a concurrent user Accept/Reject request and this scan-driven transition can never both win), with marketplaceStatus and marketplaceStatusDetectedAt set in that same guarded write.
  • 4When a removed-status Listing's externalItemId reappears among a later scan pass's results for the same Source, it atomically transitions back removed → open (same guarded-write pattern, guarding on status = 'removed' instead), clearing marketplaceStatus/ marketplaceStatusDetectedAt back to null/null — the system always reflects current marketplace reality, even if that means a Listing the user had mentally filed as done reappears in the actionable queue.
  • 5A Listing already transitioned to removed is never re-verified by a later scan while it stays removed and still missing (bounded per-item network cost: one recheck per transition, not one per listing per scan forever) — only Requirement 4's reappearance check runs against it.
  • 6eBay's per-item recheck can only ever resolve to active (still found) or removed (gone) — never sold. Confirmed via eBay's own Browse API documentation/developer forums: getItem returns an identical 404 whether an item sold or was simply delisted; the Browse API serves only active listings and has no endpoint this project is credentialed for that distinguishes the two. This is a real platform limitation, not an implementation gap — stated plainly in the connector's own code comment, not silently narrowed.
  • 7Mercari's per-item recheck can genuinely distinguish sold from removed — confirmed live during planning: a real Mercari search response's itemsList[].status field carries distinct values (on_sale, trading, and documented but not yet captured sold_out) beyond the on_sale-only set the existing connector already filters search results to. The per-item recheck re-visits that same item's own detail page (the exact technique mercariItemDetail.ts's existing description fetcher already uses) and reads its current status field from the same __NEXT_DATA__ node; confirm live during the build (not guessed) whether that node's status field carries the same values as the search response's.
  • 8Facebook Marketplace's per-item recheck is best-effort — no live dedicated-account session exists to confirm its exact signal during this work, the same documented limitation the rest of that connector already carries. Implemented the same way (direct per-item page visit in the authenticated session), flagged plainly as unconfirmed in its own code comment, not presented as equally reliable to Mercari's.
  • 9The Listings queue table shows a visible badge on any Listing currently carrying a marketplaceStatus, using the exact same shared badge convention already established there (NonWorkingBadge/EbayScanBadge), reading "Sold" or "No longer listed" per Requirement 1.
  • 10The Listings queue's existing Status filter (STATUS_OPTIONS in listing-list.tsx, the same mechanism 'accepted'/'rejected' already use) gains 'removed' as a fourth filterable value — this is not a new filter feature, it's the existing one already covering every other terminal status, now covering this one too.
