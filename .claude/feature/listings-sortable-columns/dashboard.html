Goal

The Listings page's table (ListingList/listings-page.tsx) gains click-to-sort column headers. Clicking a column header's label sorts the table by that field; clicking the same header again reverses direction; clicking a different header replaces the active sort field entirely (never combines two fields). Confirmed with the user: sorting applies across the **whole filtered dataset**, not just the 20 rows on the current page — the table is server-paginated, so a correct "cheapest first" or "oldest first" sort has to reorder every matching Listing, not just whichever page happens to be open, the same way the existing status/Source filters already operate across the whole dataset rather than the current page. Of the table's 9 columns, 7 carry a real, comparable value and become sortable: Title, Source, Status, Asking Price, Expected Resale, Difference, Identify Parts. The leading checkbox-selection column and the trailing Accept/Reject actions column carry no comparable field and stay unsortable. Two of the seven (Expected Resale, Difference) are values computed server-side per Listing (a sum over that Listing's Expected Parts, confirmed by reading routes/listings.ts's computeComparison) rather than plain stored columns, and Source's displayed value is its *name*, looked up from sourceId — all three need their real resolved value as the sort key, not a raw id or an unrelated proxy (Requirement 6).

Requirements

  • 1Each of the 7 data-bearing column headers (Title, Source, Status, Asking Price, Expected Resale, Difference, Identify Parts) is clickable and sorts the table by that field.
  • 2Clicking a column header that is not the currently active sort field makes it the active sort field, ascending.
  • 3Clicking the currently active sort column's header again reverses its direction (ascending -> descending, descending -> ascending).
  • 4Only one field is ever sorted by at a time. Clicking a different column replaces the active sort field outright (starting ascending, per Requirement 2) — it never combines with whatever was active before.
  • 5The currently active sort column and its direction are visually indicated on that column's own header (e.g. a directional arrow), distinct from every other header.
  • 6Sorting a column whose displayed value is derived, not a raw stored field, sorts by that real displayed value: Source sorts by the Source's name (not its internal id); Expected Resale and Difference sort by their actual computed numeric values (not, e.g., Asking Price as a stand-in).
  • 7Changing the active sort field or its direction resets the current page back to 1, the same way changing a status/Source filter already does today.
  • 8Sorting composes with the existing status/Source filters and with pagination: the sorted, filtered dataset is what gets paginated. Changing a filter does not silently clear or reset whichever sort is currently active.
  • 9With no sort ever applied (a fresh page load, before any header has been clicked), the table's row order is unchanged from today's default (newest listingDate first) — this feature adds a new ordering option, it does not change the existing default.
  • 10The leading checkbox-selection column and the trailing Accept/Reject actions column are not sortable — neither carries a value that could be compared.

Assumptions

  • A1Confirmed directly with the user — sorting applies across the whole filtered dataset (server-side), not just the current page's visible rows.
  • A2When sortBy is active, T2 fetches every matching Listing in one unpaginated query (listListings called with limit: total) rather than writing per-field SQL ORDER BY clauses. At this project's current scale (185 Listings total), fetching the full filtered set and sorting in application code is simpler and no less correct.
  • A3A Listing with no identify-parts job at all (identifyPartsStatus: null) sorts when sorting by Identify Parts as if its stage were an empty string — placing every such row together at one end, rather than scattering them.
  • A4Ties within one sort field keep their relative order from listListings's existing default ordering (listing_date DESC, id ASC) rather than an explicit secondary sort key, relying on Array.prototype.sort's ES2019+ stability guarantee.
  • A5R2 and R3 each flagged a FAIL on cyclomatic complexity (GET /api/listings handler at 12, ListingsPage at 12) measured with a reviewer-invoked ESLint complexity rule that is not wired into this project's real eslint.config.mjs. feature-validate-lead overruled both as non-blocking style recommendations: neither names a correctness/safety defect with a concrete failure case (both reviewers independently confirmed every behavioral requirement correct), and this exact judgment has been applied consistently across prior features.
