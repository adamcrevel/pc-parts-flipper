Goal

User-reported gap, confirmed by investigation: a scanned eBay listing's full item description and its seller-provided "Item Specifics" (structured name/value pairs eBay shows on the listing page — RAM, storage, processor, OS, GPU, etc.) are never captured at all. Confirmed directly against the user's own example, "gameing pc Ryzen 5 5600" (id c87e761e-d475-4afa-8817-31f807ad76d8, a real, already-scanned production listing): its stored description is null, and in fact **every one of the 222 real listings currently in production has description: null** — this is not an isolated bug, it is the actual behavior of the scan pipeline today. Root cause, confirmed by reading the code: scanService.ts's importCandidateIfNew hardcodes description: null on every imported Listing. eBay's search endpoint (item_summary/search, what a scan actually calls) never returns a full description or item specifics in the first place — those only exist on eBay's single-item detail endpoint (GET /buy/browse/v1/item/{itemId}), confirmed against eBay's own Browse API documentation (description: string, HTML, up to 500,000 characters; localizedAspects: Array<{name, type, value}>, the item specifics). That detail endpoint is already called elsewhere in this codebase (ebayConnector.ts's createEbayItemDetailClient), but only by the one-time manual photo-backfill script, and even then only to extract image URLs — the same response's description and localizedAspects fields are fetched and immediately discarded. This feature captures both fields (full description, HTML-stripped to plain text; every item specific eBay reports, not a curated subset) and stores them in the Listing's existing description field — the same field buildIdentificationPrompt already includes verbatim in the AI identification prompt, so no prompt-building change is needed for Requirement 6. This happens for every newly-scanned eBay listing going forward, and, via a new one-time backfill (mirroring the existing photo-backfill script's own pattern) for every eBay listing already imported without it — including the user's own example.

Requirements

  • 1A newly-scanned eBay listing's full seller-written item description is fetched (from eBay's single-item detail endpoint, the only endpoint that carries it) and stored, converted from eBay's HTML to plain text.
  • 2A newly-scanned eBay listing's full set of seller-provided Item Specifics (every name/value pair eBay's localizedAspects reports for that item — not a hardcoded subset such as only RAM/storage/CPU/OS/GPU) is fetched and stored, each pair clearly rendered as its own Name: Value line, visually distinct from the prose description.
  • 3Both are stored together in the Listing's existing description field, prose description first, then the item specifics block.
  • 4Every eBay-sourced Listing already in the database before this feature shipped, whose description is still null, is backfilled with the same description + item specifics capture — via a new one-time script following this project's own established pattern (photoBackfill.ts/backfill-photos.ts), run once against the real production database as part of delivering this feature, not left as an unused capability.
  • 5A failure fetching eBay's item detail (the item was removed, a transient API error, etc.) never prevents the Listing itself from being imported or backfilled — it is logged and the Listing's description is simply left as it was, the same graceful-degradation behavior this codebase already uses for photo downloads.
  • 6The combined description + item specifics text is available to AI part identification (buildIdentificationPrompt) without any change to that prompt-building code — proven by the fact that it already reads listing.description verbatim, so storing the richer text in that same field is what satisfies this requirement.
  • 7The additional eBay API call this feature introduces (one single-item detail call per genuinely new candidate) is bounded to scale with the number of new listings a scan actually imports, never with the full search-result set a scan merely found — matching this codebase's own existing, test-enforced "no needless per-item API call" principle (already proven by an exact HTTP-call-count test for photos, which this feature's own task must update rather than violate).

Proposals

  • Schedule a known-up-front "run this once in production" deliverable (Req 4's backfill here) as its own owned, timed task in the Cycle 0 plan itself — not as an assumption of future intent (A3) with no slot or owner. Doing so would have let Cycle 0's own UAT pass, avoiding a dedicated second cycle whose only job was to execute and re-verify a step that was foreseeable on day one.
  • When a call-budget/scaling test is specified (e.g. "bounded to new imports, not total results"), require at least one scenario mixing duplicates with new items in the task spec itself, not added reactively after a reviewer catches the gap — T2's own must_fix (A15) was exactly this: the original scenarios all had zero duplicates and so could not falsify a per-search-result regression.
  • Raise the default estimated_tokens sizing for reviewer/tester/uat roles specifically — this feature's 8 such tasks ran 2.2x-9.3x over their own token estimate while their time estimates stayed accurate, indicating the token heuristic is calibrated for builder work and under-sizes verification work by roughly 3-5x as a rule.

  • Fix measure-child-cost.py's lookup key: it returned a wrong, stale-session value on two separate passes in this one feature (A16, A17) because free-text tag grepping collides across unrelated sessions that happen to reuse generic tags like "review T2"/"test T2". Key the lookup on the dispatch's own unique transcript filename/session id instead, which is already the manual fallback being used to catch its errors.
