# Retrospective

## What happened

- **Cycle 1 existed because of one recurring failure mode, not a new one.** T5's `listing-form.tsx` change correctly added `identityCandidates: []` to every row of the Listing POST/PUT payload (Req 6). A pre-existing exact-shape `toEqual()` assertion in `apps/web/test/identify-parts.test.tsx` — a file outside T5's and TS5's own touched-file list — broke as a result. It survived cycle 0's retry 1 undetected (the retry only fixed `expected-parts-editor.test.tsx`'s fixtures) and was only caught by feature-validate-lead's standing-gate *re-run*. Per the one-free-retry-per-task-per-cycle rule, this second distinct T5 failure opened Cycle 1 as task T7 (a 3-line test-only fix), plus its review pair R7/TS7. Cost: 3 tasks, ~40 expected minutes combined, ~130k combined `actual_tokens` (44767 + 51098 + 33748), and roughly 45 real minutes (07:01–07:19 plus the already-running U1 after). The fix itself was trivial; the cost was almost entirely the review/test ceremony required to land a 3-line diff that could have been made in cycle 0.

- **The same root cause fired five separate times across cycle 0, and this is the dominant pattern in the whole feature.** Making `identityCandidates` a *required* field on `ExpectedPartRow`, `CreateExpectedPartInput`, `CreatePartInput`, `AiIdentifiedPart`/`normalizePart`'s return shape, and the four read-only-display props broke pre-existing test fixtures/exact-shape assertions in files the responsible task never touched or listed: `db.test.ts` (T2, 7 tests), `partIdentification.test.ts` + `identifyPartsRoute.test.ts` (T3, 4 tests), `expected-parts-editor.test.tsx` (T5, 14 tests), four fixture files under `apps/web/test/` (T6, 17 tests), and finally `identify-parts.test.tsx` (T5's second hit, 1 test — the one that became Cycle 1). That is 43 pre-existing test failures, all from the identical shape: "add a required field to a shared type, an untouched caller's fixture doesn't know about it." R4 and R6 both failed cycle 0's first review specifically on variants of this (R4 on T4's zero coverage of the new field's validation; R6 on T6 breaking 17 tests this same way).

- **T4's gap was a different flavor of the same family — not a fixture break, but zero new coverage for new behavior.** `teardown.test.ts` and `listings.test.ts` never got a non-empty `identityCandidates` fixture or a malformed-input case added, so Req 6 (validator accept/reject) and Req 7 (teardown carry-over) shipped production-correct but untested through cycle 0's first pass. TS4 closed this in-cycle with 6 new tests, so it didn't cost a retry — but it's the same "new field, caller not updated" shape as T2/T3/T5/T6, just manifesting as missing assertions instead of broken ones.

- **T1 carried an unrelated, one-off gap:** `packages/shared`'s `test` script was still the placeholder no-op (`echo "no tests yet..." && exit 0`), so TS1's new `partIdentity.test.ts` silently never ran under `npm test` at any level. R1 caught it; the retry wired a real `vitest run` script. This is infrastructure debt predating the feature, not a pattern repeated elsewhere in this run.

- **One informational, non-gating finding:** R3 flagged `coerceIdentityCandidates`'s cyclomatic complexity (11, measured by an ad-hoc rule the reviewer added only for measurement — the project's real `eslint.config.mjs` has no complexity rule). feature-validate-lead correctly judged this a style preference, not a must_fix, since the function was correct and fully mutation-tested. No cost beyond the judgment call itself.

- **No model escalation, no context_split, and no corrected Assumption occurred.** All 6 builder tasks (T1-T6) plus T7 ran at their planned sizing; none needed a bigger model mid-task or split into extra rows beyond the planned R/TS pairs. Every one of the 12 numbered Assumptions held through UAT without a dashboard correction.

## Proposals

- **When a plan task adds a required field to a type/interface that existing code already constructs (`Create*Input`, a row/props type, a parsed-output shape), its own task description should explicitly name every pre-existing test file that constructs or asserts on that shape, not just the files where new logic lives.** This feature's plan already named each task's *production* files carefully; it's the *existing test fixtures the new field will break* that went unnamed five times (T2, T3, T5×2, T6) and once underspecified in the other direction (T4's validation/carry-over tests). A one-line scope addition like "also update `db.test.ts`'s `createExpectedPart`/`createPart` call sites and the two column-order assertions to include the new field" would have let T2's own builder fix it in the first pass instead of costing a full must_fix/retry round.

- **Prefer `identityCandidates?: X[]` (optional, default `[]` at the read site) over a required field for any shape with pre-existing callers**, the same way T4's validator already defaults an absent field to `[]`. T2 made `CreateExpectedPartInput`/`CreatePartInput` required specifically to match sibling-field convention (A8), and that choice is what turned every untouched caller into a runtime throw instead of a silent, correct default. The convention-consistency argument is real, but for a cross-cutting additive field it cost more in review/retry rounds than it bought in type-strictness; a future feature with this exact shape (new field on an existing, widely-constructed type) should default to optional+fallback and only go required if a specific caller needs the compiler to force it.

- **Run a full-suite standing gate once, immediately after the first wave of builders lands, before dispatching any reviewers/testers**, rather than discovering the breadth of the fixture-break pattern piecemeal across five separate review findings. feature-validate-lead's cycle-0 gate did catch all of T2/T3/T5/T6's breaks in one pass (good), but R4/R6 still had to independently rediscover variants of the same root cause in their own task-scoped reviews. A single upfront `npm run test` pass surfaced to the orchestrator before task-scoped review dispatch would have let every reviewer start from "here are the N pre-existing tests this task's required field broke" instead of each reviewer finding their own slice.
