Feature

Status done · cycle 1 of 3

Goal

Right now, `POST /api/listings/:id/identify-parts` gives exactly one brand and one model/part number per part, or `null` if it can't name one confidently. This feature adds a layer under that: when the AI can't pin a part down to one answer, but can narrow it to a short list of likely answers, it reports that list instead of just giving up with `null`. That means multiple possible brands when the brand itself is unclear, or multiple possible models within one known brand when only the model is unclear. The list is saved with the Expected Part (not just shown once and thrown away), carries over to the Part made at teardown the same way brand/model already do, and shows up everywhere a part's identity already shows up. Pricing these candidates is a separate, later feature and out of scope here — this feature only makes and keeps the list.

Requirements

1. If the AI can confidently name one brand and one model for a part, nothing changes: `brand`/`partNumber` stay single values and no candidate list is made.
2. If the AI has no lead at all on a part's brand or model, nothing changes: the field stays `null` and no candidate list is made for it — an empty list isn't a guess.
3. If the AI can narrow a part to a short list of likely brands but can't pick one, it reports that list as ranked candidates (most to least likely), each paired with a model/part number where one is known for that candidate — instead of leaving `brand` as `null` with nothing else.
4. If the AI confidently knows a part's brand but can only narrow its model/part number to a short list, it reports that brand along with the list of likely models as candidates — instead of leaving `partNumber` as `null` with nothing else.
5. A candidate list is capped at a small fixed size, never has two identical {brand, model} pairs, and never repeats the single confident answer already reported for that field.
6. Once the user saves the Listing, an Expected Part's candidate list is saved with it — not dropped at save time, even if the user never picks one of the candidates.
7. When a Purchase is torn down, an Expected Part's saved candidate list carries over to the Part made for it, the same way its brand/partNumber already carry over.
8. Everywhere an Expected Part's or Part's identified brand/model already shows up today — the Listing's Expected Parts editor, the Purchase detail screen's Expected Parts table, the Teardown checklist, the Parts list table, and the Record Sale page heading — a non-empty candidate list shows next to the main identification, not just stored out of sight.
9. In the Listing's Expected Parts editor, picking one of a row's candidates fills that row's brand/model fields in one action; picking one is never required before the row can be saved.

## Proposals

- **When a plan task adds a required field to a type/interface that existing code already constructs (`Create*Input`, a row/props type, a parsed-output shape), its own task description should explicitly name every pre-existing test file that constructs or asserts on that shape, not just the files where new logic lives.** This feature's plan already named each task's *production* files carefully; it's the *existing test fixtures the new field will break* that went unnamed five times (T2, T3, T5×2, T6) and once underspecified in the other direction (T4's validation/carry-over tests). A one-line scope addition like "also update `db.test.ts`'s `createExpectedPart`/`createPart` call sites and the two column-order assertions to include the new field" would have let T2's own builder fix it in the first pass instead of costing a full must_fix/retry round.

- **Prefer `identityCandidates?: X[]` (optional, default `[]` at the read site) over a required field for any shape with pre-existing callers**, the same way T4's validator already defaults an absent field to `[]`. T2 made `CreateExpectedPartInput`/`CreatePartInput` required specifically to match sibling-field convention (A8), and that choice is what turned every untouched caller into a runtime throw instead of a silent, correct default. The convention-consistency argument is real, but for a cross-cutting additive field it cost more in review/retry rounds than it bought in type-strictness; a future feature with this exact shape (new field on an existing, widely-constructed type) should default to optional+fallback and only go required if a specific caller needs the compiler to force it.

- **Run a full-suite standing gate once, immediately after the first wave of builders lands, before dispatching any reviewers/testers**, rather than discovering the breadth of the fixture-break pattern piecemeal across five separate review findings. feature-validate-lead's cycle-0 gate did catch all of T2/T3/T5/T6's breaks in one pass (good), but R4/R6 still had to independently rediscover variants of the same root cause in their own task-scoped reviews. A single upfront `npm run test` pass surfaced to the orchestrator before task-scoped review dispatch would have let every reviewer start from "here are the N pre-existing tests this task's required field broke" instead of each reviewer finding their own slice.
