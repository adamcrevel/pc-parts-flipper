# Async Identify-Parts Queue

## Goal
Today, Identify Parts on a Listing runs the whole AI pipeline synchronously inside the HTTP request, blocking the UI for 15-45+ seconds behind a disabled button and static text. This feature moves the pipeline onto a database-backed job queue: a request enqueues a persistent job row instead of running inline, a single-worker pool (size 1, built to support more later) picks up queued jobs in the background and runs the existing identification pipeline, and the UI polls for status instead of blocking on one long request. The UI shows the job's real stage as it progresses (queued/waiting to run, identifying, sourcing reference photos, comparing photos), not a generic "in progress" spinner. Because the queue is DB-backed, an in-flight or queued job survives a server restart instead of being lost.

## Requirements
1. `POST /api/listings/:id/identify-parts` no longer runs the identification pipeline inline. It enqueues an `identify_parts_jobs` row (stage `queued`) and returns immediately (201) instead of waiting for the AI calls to finish.
2. The job row is persisted in DuckDB (`identify_parts_jobs` table), not held only in server memory, so a running or queued job survives an `npm run dev`/server restart.
3. On server startup, any job left in a non-terminal, already-started stage (`identifying`, `sourcing_references`, `comparing`) from a previous process life is reset to `queued` so it gets reprocessed from the start, instead of being silently abandoned.
4. A single background worker pool, implemented as an async concurrency-limited loop (not OS `worker_threads`), pulls `queued` jobs and runs `identifyListingParts` for each.
5. The worker pool's concurrency limit is a named constant/env override (`IDENTIFY_PARTS_POOL_SIZE`), defaulting to 1. The claim step is a single atomic SQL statement, so the mechanism already works correctly for a future limit greater than 1 rather than being hardcoded to exactly one concurrent job.
6. While a job runs, its `stage` column is updated at each pipeline transition to one of exactly: `queued`, `identifying`, `sourcing_references` (only when at least one identified part triggers reference/catalog sourcing or lookup), `comparing` (only when a second AI pass actually runs), `completed`, or `failed`.
7. `GET /api/identify-parts-jobs/:jobId` returns that job's current stage, plus its result once `completed` or its error once `failed`, so the UI can poll it.
8. `GET /api/listings/:id/identify-parts-jobs/latest` returns the most recent job for a listing (404 if none ever existed), so reopening or reloading the listing's page resumes showing the right state instead of losing track of an in-flight or just-finished job.
9. The Identify Parts UI shows the job's current stage with distinct, human-readable copy for each stage: `queued` → "Waiting to run…", `identifying` → "Reading the listing text and photos with AI…", `sourcing_references` → "Sourcing reference photos from manufacturer sites…", `comparing` → "Comparing photos against reference images…" — never one generic "in progress" message for all of them.
10. Once a job reaches `completed`, the UI automatically applies its suggested parts to the Expected Parts editor (same `onIdentified` behavior as today), with no extra click needed.
11. A job's result is applied at most once: the server tracks a `delivered` flag per job (via `POST /api/identify-parts-jobs/:jobId/ack`), so reopening a listing whose job already completed and was applied doesn't re-append the same suggested parts a second time.
12. If a listing already has an active (non-`completed`, non-`failed`) job, `POST /api/listings/:id/identify-parts` rejects the duplicate request with 409 instead of enqueueing a second job for the same listing.
13. This 409 rejection is race-free under real concurrent requests: the enqueue is one atomic `INSERT ... WHERE NOT EXISTS` statement, not a separate check-then-insert pair of queries. This is proven by a test that fires genuinely concurrent HTTP requests (not sequential calls) at the same listing and asserts exactly one job was created.
14. The Identify Parts button is disabled whenever its listing already has an active job — whether just-enqueued by this click, found via the 409 response, or discovered on page load via the latest-job lookup — and is never clickable while a job is in flight.

## Assumptions
- A1 (cycle 0): "Thread pool" means an async concurrency-limited worker loop in the main Node process, not literal `node:worker_threads` — per the user's explicit choice, because the pipeline's work (spawning the `omp` CLI, DB/HTTP I/O) is I/O-bound and the DuckDB native binding is documented single-connection-per-process.
- A2 (cycle 0): The stage set is the 4 coarse stages (plus `queued`/`completed`/`failed`) the user approved, not a finer per-sub-step breakdown.
- A3 (cycle 0): A listing with an in-flight job rejects a second POST with 409, and the button is disabled client-side while active — per the user's explicit choice.
- A4 (cycle 0): Job completion auto-applies suggested parts to the Expected Parts editor (same as today's synchronous auto-apply), tracked via a server-side `delivered` flag to prevent double-apply on reload — per the user's explicit choice.
- A5 (cycle 0): The worker pool polls the DB for queued jobs on a fixed interval, rather than being notified synchronously by the enqueue route, so a fresh job briefly shows `queued`/"Waiting to run…" even when the pool has free capacity. This also decouples the route and pool modules and directly serves the user's requested "waiting to run" status.
- A6 (cycle 0): Graceful shutdown stops the worker pool's poll loop (mirroring the existing scheduler's `ScheduledTask.stop()` wiring) so no new claim attempt starts against a closing DB connection, but it does not wait for an in-flight job to finish — matching the existing scheduler's accepted fire-and-forget shutdown behavior. - A7 (cycle 0): `IDENTIFY_PARTS_POOL_SIZE` is a plain positive-integer env var (parsed like `PORT` in index.ts), with no further validation or UI for changing it — it's an ops-level/dev knob, not a user-facing setting.
