Goal

Today, Identify Parts on a Listing runs the whole AI pipeline synchronously inside the HTTP request, blocking the UI for 15-45+ seconds behind a disabled button and static text. This feature moves the pipeline onto a database-backed job queue: a request enqueues a persistent job row instead of running inline, a single-worker pool (size 1, built to support more later) picks up queued jobs in the background and runs the existing identification pipeline, and the UI polls for status instead of blocking on one long request. The UI shows the job's real stage as it progresses (queued/waiting to run, identifying, sourcing reference photos, comparing photos), not a generic "in progress" spinner. Because the queue is DB-backed, an in-flight or queued job survives a server restart instead of being lost.

Requirements

  • 1POST /api/listings/:id/identify-parts no longer runs the identification pipeline inline. It enqueues an identify_parts_jobs row (stage queued) and returns immediately (201) instead of waiting for the AI calls to finish.
  • 2The job row is persisted in DuckDB (identify_parts_jobs table), not held only in server memory, so a running or queued job survives an npm run dev/server restart.
  • 3On server startup, any job left in a non-terminal, already-started stage (identifying, sourcing_references, comparing) from a previous process life is reset to queued so it gets reprocessed from the start, instead of being silently abandoned.
  • 4A single background worker pool, implemented as an async concurrency-limited loop (not OS worker_threads), pulls queued jobs and runs identifyListingParts for each.
  • 5The worker pool's concurrency limit is a named constant/env override (IDENTIFY_PARTS_POOL_SIZE), defaulting to 1. The claim step is a single atomic SQL statement, so the mechanism already works correctly for a future limit greater than 1 rather than being hardcoded to exactly one concurrent job.
  • 6While a job runs, its stage column is updated at each pipeline transition to one of exactly: queued, identifying, sourcing_references (only when at least one identified part triggers reference/catalog sourcing or lookup), comparing (only when a second AI pass actually runs), completed, or failed.
  • 7GET /api/identify-parts-jobs/:jobId returns that job's current stage, plus its result once completed or its error once failed, so the UI can poll it.
  • 8GET /api/listings/:id/identify-parts-jobs/latest returns the most recent job for a listing (404 if none ever existed), so reopening or reloading the listing's page resumes showing the right state instead of losing track of an in-flight or just-finished job.
  • 9The Identify Parts UI shows the job's current stage with distinct, human-readable copy for each stage: queued → "Waiting to run…", identifying → "Reading the listing text and photos with AI…", sourcing_references → "Sourcing reference photos from manufacturer sites…", comparing → "Comparing photos against reference images…" — never one generic "in progress" message for all of them.
  • 10Once a job reaches completed, the UI automatically applies its suggested parts to the Expected Parts editor (same onIdentified behavior as today), with no extra click needed.
  • 11A job's result is applied at most once: the server tracks a delivered flag per job (via POST /api/identify-parts-jobs/:jobId/ack), so reopening a listing whose job already completed and was applied doesn't re-append the same suggested parts a second time.
  • 12If a listing already has an active (non-completed, non-failed) job, POST /api/listings/:id/identify-parts rejects the duplicate request with 409 instead of enqueueing a second job for the same listing.
  • 13This 409 rejection is race-free under real concurrent requests: the enqueue is one atomic INSERT ... WHERE NOT EXISTS statement, not a separate check-then-insert pair of queries. This is proven by a test that fires genuinely concurrent HTTP requests (not sequential calls) at the same listing and asserts exactly one job was created.
  • 14The Identify Parts button is disabled whenever its listing already has an active job — whether just-enqueued by this click, found via the 409 response, or discovered on page load via the latest-job lookup — and is never clickable while a job is in flight.

# Retrospective

## What happened

This was a clean, single-cycle run: Cycle 0 only, no cycle increment. The four builders (T1-T4),
eight paired reviewer/tester rows (R1-TE4), and UAT (U0) all completed in one pass each. The
"four in-place retries" were not a second cycle — they were must_fix items from validate-lead's
*first* standing-gate pass, folded back into T1-T4's own rows and fixed without re-dispatching a
new task id. That folding is itself worth flagging (see Proposals): because the retry text was
merged into the original row rather than logged as a delta, the table's actual_tokens and
started_at/completed_at for T1-T4 cannot be cleanly split into "first pass" vs. "fix pass" —
this retrospective can only report the combined figure per task, not the retry's isolated cost.

- **The single biggest finding**: all four must_fix items were things no reviewer or tester caught,
  and all four were caught only by validate-lead's own standing-gate run, not by any task's R/TE
  pair. Two were cross-file breakage outside the task's own named scope: T1 added
  identify_parts_jobs to schema.ts but didn't update apps/server/test/db.test.ts's hardcoded
  EXPECTED_COLUMNS/table-count fixture (A13); T4 deleted identifyListingParts from

  failed with a deterministic TypeError (A13). The other two were logic bugs inside scope but of a

  async resumeJob closure (A14) — nobody ran npm run build/tsc -b before validate-lead did.

  change (T2: defensive env parsing; T4: TS-narrowing fix + unused-import removal + rewriting a

## Proposals

- **Make npm run build (or each workspace's own tsc -b) part of every reviewer's or tester's own
  checklist, not only validate-lead's final standing gate.** vitest does not type-check, so a
  build-breaking type error (T4, TS18048) reached the last gate in the pipeline before being caught.
  Running the one-line build command per task is cheap relative to the cost of a cross-cutting fix
  landing at validate time.

- **When a task deletes or renames an exported function/table/column, require its own reviewer or
  tester to grep the whole test tree for the old identifier before marking the task complete**, not
  just the files named in the task's own scope. Both deterministic Cycle-0 regressions (T1's
  db.test.ts fixture, T4's api-client.test.ts) were exactly this shape — a rename/add/delete
  whose blast radius crossed into a test file the task's reviewer/tester scope didn't name. A
  one-line grep -r <old-identifier> catches this class before it reaches validate-lead.

- **Log in-place retry cost as an explicit delta in the Cycle Log (tokens and minutes spent on the
  fix alone), rather than folding the fix description into the original task row and leaving
  actual_tokens/started_at/completed_at as the combined, unsplit figure.** As written, this
  plan.md makes it impossible to say how much of T1-T4's reported cost was the original build vs.
  the Cycle-0 fix — which is exactly the kind of number a retrospective exists to extract.

- **Fix measure-child-cost.py's tag-matching so a sub-agent's own dispatch name reliably resolves
  to that sub-agent's transcript**, since it returned null for all 8 reviewer/tester children in
  this run (A19) and a looser guess returns contaminated numbers from unrelated sessions. Until
  fixed, no retrospective on any feature can measure reviewer/tester cost at all — only builder cost
  survives in the table.

- **Have the dispatcher set each sub-agent's shell cwd to the worktree path directly (not just
  mention it in the prompt), and have the sub-agent verify with git status --short in that cwd
  before its first edit.** A12 shows a bare relative path can silently resolve against the main repo
  checkout instead of the worktree; this time it was caught, but catching it relied on a human
  noticing a stray diff rather than on the dispatch mechanism preventing it.
