Goal

Fix two problems in the Identify Parts flow. First, running Identify Parts again on a Listing that already has Expected Parts duplicates them instead of replacing them — persistIdentifiedParts only ever inserts, never removes old entries. Second, the AI identification/comparison calls behind this flow still use a 120-second timeout sized for a synchronous request, even though the flow now runs as an asynchronous background job that the client polls; a slow-but-working call can get cut off, producing an avoidable timeout error.

Requirements

  • 1persistIdentifiedParts (apps/server/src/jobs/identifyPartsWorkerPool.ts), which only runs once an identify-parts job finishes successfully, must delete every Expected Part already on the job's Listing — using the same listExpectedPartsByListing + deleteExpectedPart pattern already used by the manual Listing-save route (apps/server/src/routes/listings.ts's PUT /api/listings/:id, lines 205-206) — before inserting the parts the job just identified. This is a full replace, not a merge: a part that existed before the run but isn't in the new result is removed; a part that didn't exist before but is in the new result is added.
  • 2A job that fails, or hasn't yet reached completed, must never delete or change the Listing's existing Expected Parts — the replace described in Requirement 1 only happens on the already-guarded successful-persistence path inside processJob's try block, and nothing else changes there.
  • 3DEFAULT_OMP_TIMEOUT_MS (apps/server/src/ai/ompRunner.ts) — the per-call limit for both the "identifying" and "comparing" AI steps of the identify-parts pipeline — goes up from 120 000ms (2 minutes) to 240 000ms (4 minutes): double the original, while staying strictly below DEFAULT_OMP_SOURCING_TIMEOUT_MS (300 000ms, reference-photo sourcing) so ompSourcingRunner.test.ts's existing invariant — sourcing's own timeout must stay longer than identification's, since sourcing does real multi-site browsing per part and is inherently the slower operation — keeps holding. Its doc comment is rewritten: the original 120s value was chosen for a synchronous request ("short enough that a wedged child process cannot pin a request open indefinitely"); since that call now runs inside an asynchronous background job limited by a worker-pool slot rather than an open HTTP request, the new comment should explain that instead.

## Proposals

- **Check cross-constant invariant tests at plan-authoring time, not after a build attempt.** T2's
  300\_000→240\_000 correction (A3) was only caught by the orchestrator's own pre-handoff check
  after a builder had already implemented the original, wrong-by-invariant value. The break was
  knowable by reading ompSourcingRunner.test.ts's existing toBeGreaterThan relationship before
  writing Requirement 3's number into the plan at all. Add to planning: when a requirement changes
  a numeric constant that another file's test asserts a relationship against (greater-than,
  ratio, etc.), read that test first and size the new value to satisfy it, rather than discovering
  the violation during or after the build.
- **Record pre-freeze self-corrections the same way A3 records a post-freeze one.** The premature
  reviewer/tester-row creation and the builder fabrication this feature's own assignment names both
  happened but left nothing in plan.md/plan-cycle0.md for a retrospective to verify directly —
  only A3-style corrections that happen to straddle a snapshot boundary get preserved. Add a
  one-line Cycle Log or Assumption note at the moment any self-correction is made, even if it's
  reversed before the next frozen snapshot, so retrospectives don't have to rely on out-of-band
  testimony for process-level findings.
- **When a task's fix touches a shared test mock barrel, grep all files importing that barrel for
  the same gap in the same pass, not just the one named in the task.** T1's db-call changes broke
  identifyPartsWorkerPool.test.ts (caught by TE1, in-scope) and separately broke
  identifyPartsPriceTrigger.test.ts (caught later, only when the full suite ran, out of TE1's
  named scope). A single grep -l for the shared barrel's import across apps/server/test/ at the
  point TE1 extends the mock would have caught both in one pass instead of two.
- **Resolve role-aliased model dispatch (feature-reviewer-small/feature-tester-small, not a
  literal model string) before the first attempt, not after a failure.** derek-zoolander failed
  for both R2 and TE2 and had to be corrected by Main mid-run to the role/size-based dispatch. Since
  this is now a known-working substitution pattern (recorded directly in both rows), default new
  dispatches straight to the role-and-size form and skip the literal-model-string attempt entirely.

Assumptions

  • A1"Identify Parts" is only ever reachable from the Listings page's edit form, before a Listing becomes a Purchase/Teardown — teardown_results.expected_part_id references expected_parts(id) with no ON DELETE CASCADE, so deleting an Expected Part that a teardown has already recorded against would orphan that reference. This is an existing, accepted risk: the manual Listing-save route (the same precedent Requirement 1 follows) already deletes and recreates every Expected Part on every save with the same exposure, undocumented and unguarded today — so Requirement 1 carries exactly the same risk as code already in production, not a new one.
  • A2No database transaction wraps the delete-then-insert in Requirement 1, matching the codebase's own established pattern (the manual-save route, and every other write path in this project — no file anywhere uses BEGIN TRANSACTION). If an insert fails partway through after the delete (e.g. the N+1th createExpectedPart call throwing), a Listing could end up with fewer Expected Parts than either the old or new set. Adding transactional safety here, when the rest of the codebase has none, would be a cross-cutting change outside what was asked for.
  • A3Requirement 3's new value (240 000ms) is double the original 120 000ms — addressing the user's report of an observed ~2-minute cutoff — while staying strictly below DEFAULT_OMP_SOURCING_TIMEOUT_MS (300 000ms) specifically to preserve ompSourcingRunner.test.ts's existing toBeGreaterThan invariant test between the two constants (caught during this orchestrator's own pre-handoff check of T2's first build attempt, which had used 300 000ms — an equal, not greater, value — breaking that test). No new timing data was gathered beyond this existing-test constraint and the user's reported cutoff.
  • A4No other timeout in the identify-parts pipeline needed changing. DEFAULT_OMP_SOURCING_TIMEOUT_MS (reference-photo sourcing, 5 minutes per call) and the client's job-stage polling (identify-parts-button.tsx's startPolling, which has no poll-count give-up of its own, unlike the separate price-estimation polling) were both reviewed and found already consistent with the async job model — left untouched since the user's report named only the ~2-minute figure Requirement 3 fixes.
