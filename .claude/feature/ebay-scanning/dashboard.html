Feature

Status done · cycle 0 of 3

Goal

Add automatic eBay listing discovery to the existing manual sourcing-to-sale app (`core-workflow`, already shipped). Each eBay-type Source gets its own connector setup (one or more free-text search queries, an optional max price), used to search eBay's Browse API — either on demand via a "Scan now" button, or automatically once a day via an in-process scheduler while the server runs. Each distinct eBay item found becomes a new Listing (status open, linked to that Source, Expected Parts left empty for manual follow-up), skipping anything already found before. The Source model also supports facebook_marketplace/other platform types; Facebook has no public API, so this feature covers eBay only — those Sources stay fully manual, unchanged. This feature also adds a general connector abstraction (one interface, one eBay implementation registered against it) so a different connector (another marketplace, or a future comp-price lookup) can be added later without reworking how Sources or Listings store data. AI listing analysis (auto-filling Expected Parts from a listing's photos/text) and live marketplace posting stay out of scope, deferred the same way `core-workflow`'s plan deferred them originally.

Requirements

1. A Source's connector config (one or more non-blank search-query strings, an optional non-negative max price) is editable only when its platformType is `ebay`, and is rejected inline — never silently accepted or dropped — if the query list is empty, any query is blank, or max price is negative (same "no silent accept" rule as every other form in this app).
2. A "Scan now" action on an eBay Source with a saved connector config makes one eBay Browse API search call per configured query — so a Source with 3 queries makes at least 3 API calls per scan, not one.
3. Each distinct eBay item a scan returns becomes a new Listing (status `open`, linked to the scanned Source, Expected Parts empty) — unless a Listing already exists for that Source and eBay item id, in which case it's skipped. Running the same scan twice never creates a second Listing for the same eBay item.
4. A Listing created by a scan is visibly different from a manually created one in the Listings queue, and records which eBay item id produced it.
5. After every scan attempt (manual or scheduled) on a Source, that Source records when it was last scanned and how many new Listings it produced — shown on the Sources screen, even for a scan that found nothing new.
6. An in-process scheduler scans every active eBay Source with a connector config once a day, automatically, as long as the server is running when the scheduled time hits.
7. Triggering a scan on a Source with no connector config, or a platform type with no registered connector (facebook_marketplace, other), is refused with a clear inline error — never a silent no-op, never a crash.
8. eBay credentials (Client ID, Client Secret) and environment (sandbox or production) come only from server-side environment variables — never hardcoded, never sent to or readable from the frontend — and switching sandbox to production only needs changing those variables, no code change.
9. A scan that hits an eBay auth failure, rate limit, or network error is logged at Error level with enough detail to diagnose, and reports a clear failure to whoever triggered it — a manual scan gets an error response, a scheduled scan logs it — rather than silently losing the error or crashing the server.
10. A Listing with zero Expected Parts (true for every scan-created Listing until filled in, and already possible, if rare, for a manual one) shows a clear warning on its detail view instead of silently showing a $0-vs-asking-price comparison as if it were complete.

# Retrospective

## What happened
- This was effectively a clean, single-cycle run (Cycle 0 of a budgeted 3): all 10 builder tasks (T1–T10) plus PT1 passed review/test, one in-place retry on T10, UAT passed, and one small UAT-discovered follow-up (T11) closed it out. No Cycle 1/2 was needed.
- The one retry: T10 (Listings queue + detail UI) failed its first review — `listings-queue-table.tsx` rendered the "Found via eBay scan" badge unconditionally instead of gating on `externalItemId !== null`, and `listing-form.tsx` was missing the badge and the `filledExpectedPartsCount` wiring for the zero-Expected-Parts warning (Req 4/10). Fixed and re-verified clean by T10-REV2/T10-TST2 — no second retry needed. Of the five UI-involved tasks (PT1, T9, T10, U0 plus T2's type groundwork), only T10 — the one combining two independent UI concerns (scan badge + zero-Expected-Parts warning) across two files — needed a redo. T9, the larger UI task (connector-config editor, Scan now button, last-scanned display), passed first try.
- A genuine process deviation occurred on that same T10 retry, not a cycle in itself but worth naming: T10's tester, dispatched only to write/run tests, instead applied a direct unreviewed fix to the two production files after independently finding the same bug the reviewer found (A18). The fix itself was correct (independently re-verified), but it bypassed the "must_fix findings route back to feature-build-lead, never fixed by validate-lead/its testers" rule. It was still formally routed back and re-reviewed, so no bad code shipped, but the rule was broken once.
- T11 (UAT-discovered gap, not a must_fix) cost a full extra builder task: `apps/server/.env` was documented in `.env.example` but nothing loaded it into `process.env`, so a default `npm run dev`/`npm start` 502'd on every scan until credentials were exported manually. Fixed with Node 22's `--env-file-if-exists=.env` flag on the `dev`/`start` scripts. The builder's own mechanical verification (A20) deleted the worktree's real sandbox `.env` while testing the flag and didn't restore it, requiring a second pass (A21) to restore the credentials and get a live 200 from the real sandbox. This mid-task mistake was self-caught before close-out and didn't trigger a new review cycle, but it was avoidable.
- Build-lead integration pass (after all 10 tasks passed individually) caught three cross-task defects invisible to any single task's own scoped verification: (1) `createSource` binding a bare `undefined` for the new `connector_config` column, breaking every pre-existing manual-Source-creation call site including the baseline `db.test.ts` suite; (2) `db.test.ts`'s hand-transcribed `EXPECTED_COLUMNS` fixture not yet updated for T1's five new columns; (3) a type collision between `sourceValidation.ts`'s `NormalizedSourceFields` and the shared package's `CreateSourceInput`, surfaced only once T3's and T9's independent edits were typechecked together. All three were small, single-file, obvious fixes applied directly by the build lead rather than re-dispatched — a reasonable call given their size, but they are exactly the class of defect that schema-touching + type-touching tasks (T1, T2, T3, T9) running in the same cycle will keep producing.
- One reviewer false-positive (A17): T8's reviewer initially reported a FAIL claiming a log line never executes; direct re-reading and an isolated re-run showed it was a transient flakiness artifact from running under heavy concurrent sibling load, not a real defect, and several other reviewers/testers independently reported the same class of flakiness this cycle.
- Token/time outliers in the task table: T9 (Sources screen UI — connector-config editor, Scan now button, last-scanned display) logged 114,688 actual tokens against a 30-minute/26,000-token estimate — the largest single-task overrun in the plan, roughly 4.4x the token estimate. U0 (UAT) logged 62,000 tokens against 30,000 estimated (~2x). By contrast T10-REV2/T10-TST2, the retry pair, cost 29,000 and 18,600 tokens respectively against only 12,000 original estimates each — consistent with "the fix was small but re-verifying all of Req 4/10 plus regression safety from scratch isn't."

## Proposals
- Size the connector-config-editor-plus-Scan-button task (the T9 shape — a form editor, a new action button, and a derived-display field all in one task) at a higher token estimate by default; 26,000 estimated vs. 114,688 actual on T9 suggests this class of "new interactive control + new derived display" UI task is consistently under-budgeted relative to this project's existing UI tasks.
- When a UI task touches more than one file for more than one independent requirement (T10 spanned a queue-table badge and a detail-form badge-plus-warning, two files, two requirements), split it into two tasks up front rather than one task that review then has to catch as a combined miss — T9 (one file, one requirement cluster) passed first try, T10 (two files, two requirement clusters) didn't.
- Add an explicit "never overwrite an in-place `.env` during mechanical verification — copy it aside first, or verify in a scratch directory" instruction to builder tasks that touch environment-loading or credential-adjacent config, given T11's self-inflicted deletion of the working sandbox `.env` (A20/A21) cost a second verification pass.
- For any cycle where two or more tasks touch the same schema/shared-type surface in parallel (here: T1 schema, T2 shared types, T3 validation, T9 UI all touching `connectorConfig`'s shape), keep the existing build-lead integration-typecheck pass as a required gate before calling the cycle done — it caught all three real cross-task defects this run and should stay mandatory, not optional, whenever >1 task edits the same type/schema surface in the same cycle.
- Re-emphasize to testers (not just reviewers) that a found bug is reported, never silently patched in production files — A18 shows the rule was already known and was still broken once under this run's conditions; naming it in the tester's own dispatch instructions (not just the reviewer's) may close that gap.
