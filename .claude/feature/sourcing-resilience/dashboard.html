Goal

Two real, live-observed failure modes are currently treated as permanent, un-retryable dead ends, discarding real information the AI model never actually got a chance to produce: 1. Sourcing-attempt level: reference-photo sourcing (referenceSourcingOrchestrator.ts) and catalog-mode sourcing (catalogSourcingOrchestrator.ts) each record one attempt per (category, brand[, partNumber]) combo, *ever* — a unique DB index blocks any future retry. Observed live (user's own screen, via omp's internal headed Chrome-for-Testing window) at IDENTIFY_PARTS_POOL_SIZE=8: HTTP 429 rate-limiting on crucial.com and a bot-detection "confirm you're human" block on zotac.com. Both get recorded as a normal, permanent succeeded:false attempt today — that combo's reference photo is now permanently un-sourceable, even though the model never got a genuine chance to search. 2. Job level: identify-parts and price-research jobs (identifyPartsWorkerPool.ts, pricePartsWorkerPool.ts) mark a job permanently failed on ANY thrown error from the omp call or its parser, with zero automatic retry. Observed live: during a ~2 hour window when the operator's own Claude account hit its usage limit, 13 of 185 queued identify-parts jobs failed with 'omp' exited with code 1 ... (is it installed and logged in?) and are now stuck failed forever, solely because of a transient, unrelated outage. Both cases share one principle (confirmed explicitly with the user): an **infrastructure failure** (a thrown error at any level, a timeout, a non-zero exit, or — newly — a clean model response that explicitly reports it was blocked) is not a genuine "searched and found nothing" signal, and must not permanently foreclose a retry. Only a clean, structurally-valid "not found" response continues to permanently block future attempts for sourcing; job-level failures have no such genuine-failure case at all (confirmed by reading both worker pools in full — see Assumption A3), so every job-level failure besides "the Listing was deleted" is retry-eligible. This feature adds, together: - Per-brand sourcing concurrency cap: no more than SOURCING_PER_BRAND_CONCURRENCY (default 1, env-configurable) omp sourcing calls for the same brand run at once — brand is used as a practical proxy for "which manufacturer site is about to get hit" (see Assumption A1). Overall identify-parts pool concurrency (IDENTIFY_PARTS_POOL_SIZE=8) is explicitly unchanged — this is a narrow per-brand cap inside sourcing, not a global throttle. - Exponential-backoff retry on infrastructure failure, at both the sourcing-attempt level (reference-photo and catalog paths) and the job level (identify-parts and price-research), with no cap on retry count (see Assumption A2) — the same growing, self-limiting backoff schedule throughout, reusing one shared helper. - A blocked signal in the two sourcing AI responses, so the model itself can report "I was rate-limited / shown a CAPTCHA / otherwise denied access" distinctly from "I searched and found nothing" — the only way to tell these apart when the omp call itself still exits 0 with a structurally-valid response. - Extending the harden-ai-json-parsing fix to three more parsers. While investigating this feature, live logs from the still-running 185-listing batch showed the identical prose-wrapped-JSON failure the prior feature fixed in identificationParser.ts/ visualComparisonParser.ts is also occurring, unfixed, in catalogSourcingParser.ts and imageSourcingParser.ts (both already in scope here for the blocked field), and in priceEstimationParser.ts (a separate pipeline, included per explicit user direction after this was surfaced) — e.g. a real captured catalog-sourcing response, "Confirmed — https resolves fine...\n\n{\"products\":[{...real valid JSON...}]}", was discarded as unparseable moments before this plan was drafted.

Requirements

  • 1A sourcing attempt (reference-photo or catalog) that fails due to an infrastructure problem — a thrown error at any level (spawn failure, non-zero exit, timeout) from the omp call, OR a clean model response that explicitly reports blocked:true — is retried later with exponential backoff, instead of being permanently recorded as "attempted, never retry."
  • 2A sourcing attempt that completes cleanly and reports a genuine not-found (image sourcing: found:false, blocked:false; catalog sourcing: zero products with blocked:false) continues to be permanently recorded and never retried — today's dedup behavior for a genuine not-found is unchanged.
  • 3The backoff interval grows exponentially with each successive infra failure for the same combo, capped at a maximum interval so it never waits unboundedly long, but with **no cap on the number of retries** — a combo that keeps hitting infra failures is retried forever, increasingly rarely, since an infra failure alone can never prove a combo is "truly unfindable" (explicit user direction).
  • 4Concurrent omp sourcing calls are capped per brand: no more than SOURCING_PER_BRAND_CONCURRENCY (default 1, env-configurable, same validation convention as IDENTIFY_PARTS_POOL_SIZE) sourcing calls for the same brand run at once; a call beyond the cap waits its turn rather than failing or being silently dropped. Overall identify-parts concurrency is unaffected — this is scoped to sourcing calls only, keyed per brand, not a global sourcing throttle and not a change to IDENTIFY_PARTS_POOL_SIZE.
  • 5An identify-parts job that fails for any reason **other than its Listing having been deleted** (every omp-call failure, every parser failure) is retried later with the same exponential-backoff schedule as Requirement 3, instead of being permanently marked failed. A job whose Listing no longer exists continues to fail permanently and immediately (retrying can never make a deleted Listing reappear).
  • 6A price-research job that fails for any reason is retried the same way — price-parts jobs have no genuine-business-failure outcome today ("no confident price" is already a completed, non-failure result; confirmed by reading priceEstimationParser.ts's own contract), so every job-level failure here is infra-retry-eligible with no permanent-failure case at all.
  • 7A job queued for retry is indistinguishable, from the outside, from a normal fresh queued job — same stage, same polling/UI behavior — until its backoff window reopens and it is claimed again. No new job stage, no UI change (this feature touches apps/server only).
  • 8The two sourcing AI prompts/parsers (image sourcing, catalog sourcing) gain a blocked boolean field the model can set alongside its existing found/not-found shape, with explicit prompt instructions distinguishing "I was rate-limited/CAPTCHA'd/denied access" from "I searched and found nothing" — the only way to classify Requirement 1 vs Requirement 2 for a call that completes without throwing.
  • 9The same prose-wrapped-JSON parsing fallback the harden-ai-json-parsing feature added to identificationParser.ts/visualComparisonParser.ts (extractBracketedJson, tried only after a direct parse fails) is also applied, unchanged in mechanism, to catalogSourcingParser.ts, imageSourcingParser.ts, and priceEstimationParser.ts. A genuinely malformed/no-JSON-at-all response still fails (sourcing parsers) or still resolves to "no confident price"/"not found" (price estimation) exactly as it does today — this only recovers a response that already contains a complete, valid JSON payload somewhere in its text.
  • 10No existing DDL pattern is violated: every new column is added via plain ALTER TABLE ... ADD COLUMN IF NOT EXISTS (never ALTER COLUMN/DROP COLUMN/ADD CONSTRAINT, which DuckDB rejects on any FK-referenced table), and no code relies on current_timestamp inside an ON CONFLICT ... DO UPDATE SET clause (a known DuckDB defect — see Assumption A5); timestamps involved in any multi-step record/retry write are computed once in application code and bound as parameters.
